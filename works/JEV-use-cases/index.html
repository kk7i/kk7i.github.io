Jev · TypeSafe AI System One Model

Jev：8 个真实用例
从输入到结构化决策的完整拆解

John Lindquist（egghead.io 创始人）在 Lenny's Newsletter 的分享。他演示的是一种根本不同的模型使用范式：把 AI 嵌入软件的方式，从“生成文本后解析”变为“直接返回结构化决策”。

📅 2026-09-30 🎙️ How I AI 播客 · Claire Vo 主持 ⏱️ 约 40 分钟

💡 一句话抓住本质

Jev 不是一个更小的 ChatGPT。它是决策引擎：你给它一个输入，再加上一个事先定义好的选项集合，它直接返回“选哪一个 + 置信度多少”。没有生成文本，没有解析，没有猜测——代码拿到结果就能直接执行。模型负责判断，你的代码负责执行。

名字来自 19 世纪经济学家威廉·斯坦利·杰文斯（Jevons Paradox）：当决策成本趋近于零，对决策的需求反而会激增。TypeSafe AI 把这一直觉做成了产品。

📖 先理解四个关键词

“带校准概率的结构化决策”——我们把它拆成四块，逐一看清。

❌ 普通 LLM 的做法

输入
“这是拿铁还是卡布奇诺？”
↓
输出（一段文本）
“嗯，根据我的观察，这杯咖啡表面有丰富的奶泡，奶泡比较厚，可能是卡布奇诺，但也可能是拿铁……”
↓
你的代码要做的

✅ Jev 的做法

输入 + 固定选项
“这是拿铁还是卡布奇诺？”
[拿铁, 卡布奇诺]
↓
输出（一个对象）
{ choice: "卡布奇诺",
confidence: 0.87,
scores: { 拿铁: 0.13,
卡布奇诺: 0.87 } }
↓
你的代码要做的
判断 confidence > 0.8 → 直接下单
🎯 结构化

输出不是自由文本，而是类型化的对象。Jev 有三种提问原语：Choice（从最多 255 个选项里挑一个）、Score（在 2–10 档量表上给分）、Noul（是/否判断，返回 0–1 概率）。输出空间在调用前就已固定。

📊 概率

Choice 返回每个选项的概率分布（总和为 1），Score 返回概率加权的档位位置，Noul 返回“是”的概率。像天气预报说“降水概率 80%”一样，你知道这个决策有多确定。

⚖️ 校准

当 Jev 说 confidence = 0.8，那它在 80% 的情况下确实是对的——这是经过 RLCD 训练验证的统计特性，而非模型的主观自信。

“校准”为什么重要？普通 LLM 的 token 概率常常过度自信——它说“99%”的时候，实际可能只有 60% 是对的。Jev 的概率经过校准，所以你可以直接用阈值做自动化决策。关键原则：阈值不是一个数，它随风险分层。
> 0.90自动执行，无需人工介入 0.75 – 0.90执行 + 写入日志，便于事后抽查 0.55 – 0.75标记为“待人工复核”，附带模型建议答案 < 0.55拒绝执行，升级到更大的模型或人工处理

1

实时语音待办应用

⚡ 零延迟

场景与挑战

用户在做别的事时随口说一句“提醒我明天下午三点跟 Sarah 开会”，希望在句子还没说完的时候，应用就已经把待办创建好了。

传统 LLM 每次调用需要 1.5–3 秒：用户说完 → 上传 → 等待 → 收到文本回复 → 解析出意图。体验上出现明显断裂。

Jev 把整个链路压缩到 约 200 毫秒：语音流式转写完成后，Jev 立刻返回结构化的 action 和槽位，应用直接创建待办，用户感知不到任何停顿。

拆解：输入 → 选项 → 返回

输入 "嗯，提醒我明天下午三点跟 Sarah 开会"
选项 添加待办 完成待办 删除待办 查询待办 修改待办
返回
intent: "添加待办" conf: 0.96 slots: { title: "跟 Sarah 开会" due: "2026-10-02T15:00" }
置信度策略 conf > 0.9 直接创建；0.7–0.9 回显“我理解为你要添加…”让用户确认；< 0.7 追问“你是想添加还是查询？”
应用层要点
  • 流式转写 + 同步调用：Jev 的 200ms 延迟允许在语音转写完成前就提交部分文本，进一步压缩端到端延迟。
  • 日期/时间不要交给 Jev：TypeSafe 文档明确说明 Jev 当前版本按字面读取指令，不擅长计数，日期视为文本——确定性逻辑保留在代码中，用 chrono 或 date-fns 解析日期。
  • 幂等保护：语音识别可能重复触发，在代码层用 request_id 做幂等去重，避免创建重复待办。
2

自然语言 → 函数名

🔀 语义路由

场景与挑战

语音助手或客服 chatbot 最常见的需求：把用户说的话直接转成可执行的函数调用。

传统 LLM 走的是“function calling”路线——模型先输出一段 JSON 描述，再由调用方解析。每多一层解析就多一次出错机会，而且模型可能生成多余解释、参数名写错、或用不在列表里的函数。

Jev 把可用函数列表直接作为选项空间：输出只能是预定义函数名之一，参数也从固定的槽位提取。“无幻觉”的真正含义不是“从不犯错”，而是“结构上不可能返回你选项之外的值”。

拆解：输入 → 选项 → 返回

输入 "把牛奶加入购物车"
选项 addToCart removeFromCart viewCart searchProducts checkout
返回
fn: "addToCart" conf: 0.98 args: { item: "牛奶" }
置信度策略 conf > 0.9 直接执行；0.6–0.9 询问“你是想加入购物车吗？”；< 0.6 回退到通用对话模型。
应用层要点
  • 函数签名 = 选项列表：把每个可用函数作为一个 Choice 选项，函数参数的 schema 写在 instructions 里，用点号路径引用 state 字段。
  • 善用并行问题：一次调用可以同时判断“意图函数”和“参数提取”两个独立问题，13 个问题合成一次调用比拆成 13 次单独调用便宜 11.5 倍、快 9.6 倍。
  • 参数校验留在代码里：Jev 提取的槽位值需要经过你的代码校验（类型、范围、枚举合法性），不要让模型直接触发副作用操作。
3

数据去重与记录合并

📊 置信度驱动

场景与挑战

CRM 导入、用户清洗、订单合并——脏数据里的重复记录永远是最费人力的部分。

字符串相似度算法（如 Levenshtein）在这里几乎没用：“John Smith”和“J. Smith”只差几个字符，“张三”和“张 三”看着一样却不同人。真正的判断需要语义理解——“这两条记录是否指向现实中的同一个实体”。

Jev 用成对比较 + 校准置信度完成这件事。10 万对记录的成本约 $0.02，传统 LLM 处理同样规模需要 $50+。

拆解：输入 → 选项 → 返回

输入 A: {name:"John Smith", email:"js@a.com"}
B: {name:"J. Smith", email:"js@a.com"}
选项 同一实体 不同实体
返回
decision: "同一实体" conf: 0.94
置信度策略 > 0.9 自动合并；0.6–0.9 进入人工复核队列；< 0.6 视为不同实体。
应用层要点
  • 先用廉价规则做候选筛选：不要对 N 条记录做 N² 次 Jev 调用。先用 email 精确匹配、电话后四位等做粗筛，只对候选对调用 Jev。
  • 问题措辞要正向：问“这两条记录是否指向同一实体”比“这两条记录是否不同”准确率更高。
  • 把置信度当“风险预算”用：高置信度自动合并，中置信度标记“可能重复”给人工一键确认，低置信度直接跳过。
4

多级应用路由

🧭 路由器架构

场景与挑战

一个复杂的 SaaS 应用有几十个页面。用户说“我想退掉上个月买的鞋子”，系统需要把他导航到退货流程的正确入口。

传统做法是 intent classification：需要大量标注数据训练分类器，规则一旦过期就失效，而且很难处理组合意图。

Jev 作为逐级路由器：每一级只面对当前页面的可选路径，输出下一步决策。它的最佳定位是嵌入 Agent 的“路由层”，而不是替代整个应用逻辑。

拆解：输入 → 选项 → 返回

输入 "我想退掉上个月买的鞋子"
选项 订单相关 退货退款 账户设置 支付问题 帮助中心
返回
route: "退货退款" conf: 0.91 next: "选择订单"
置信度策略 > 0.85 直接跳转；0.6–0.85 展示前两个候选让用户选；< 0.6 回到主菜单。
应用层要点
  • 路由问题是 Agent 架构的核心瓶颈：当文本模型回答“该调用哪个工具”时，它可能发明一个不存在的工具；Jev 只从你给的选项中返回，永远不会返回第四个。
  • 逐级路由 = 代码控制流：每一步 Jev 调用返回后，由代码决定是否进入下一级。不要在 Jev 内部做多步推理——它不是 System 2 模型。
  • 用 state 给 Jev 上下文：在 instructions 中引用用户的历史行为字段（如 user.last_order_id），让路由决策更有依据。
5

棋类对弈 · 速度与成本基准

♟️ 基准测试

场景与挑战

John 用一个极端场景来展示 Jev 的定位：让 Jev 和低推理 LLM 下一盘闪电棋，看谁在实际对弈中表现更好。

普通 LLM 每步需要 5–15 秒，成本约 $0.01/步，根本无法做实时对战。而且它的输出是自然语言，需要额外的解析层把“我建议走马到 f3”转成 Nf3。

Jev 以约 0.3 秒/步的速度“蜘蛛式”遍历约 30 个合法走法，返回 top-3 候选和分数。每步成本不到 $0.0001。

拆解：输入 → 选项 → 返回

输入 当前棋盘状态（FEN 字符串）
选项 约 30 个合法走法（由棋盘状态生成）
返回
top3: [ { move: "Nf3", score: 0.82 }, { move: "e4", score: 0.76 }, { move: "d4", score: 0.71 } ] conf: 0.82
置信度策略 这里比的不是“谁更聪明”，而是“单位决策成本谁更低”。Jev 不是国际象棋引擎，它证明的是：需要快速遍历决策空间的场景，Jev 的成本结构完全不同。
应用层要点
  • 用 Score 原语做排序：当选项之间有递进关系（如“好/较好/一般/差”），用 Score 而不是 Choice，因为 Score 能表达“主要落在第 1 档、有一点落在第 2 档”的微妙差异。
  • Top-K 而非 Top-1：让 Jev 返回概率最高的前 3 个候选，你的代码可以在候选间做二次筛选（比如排除不合法的走法），提高整体准确率。
  • 成本结构决定架构：当单次决策成本低于 $0.0001，你可以设计“每个事件都调用 Jev”的架构，而不是传统 LLM 时代的“批量处理 + 缓存”模式。

多步分类流水线

🔗 链式调用

场景与挑战

当分类空间很大（比如客服工单有 20+ 类别），一次性把所有选项丢给模型，准确率会显著下降。模型容易在大列表里“看花眼”。

John 的做法是把一次分类拆成多步树形分类：每步只面对 3–5 个选项，逐步缩小范围。虽然总调用次数增加，但每次 Jev 调用的成本低到可以忽略不计。

更关键的是：多因素判断要拆开，在代码里加权合成。不要问“给这个创业 pitch 打分”，而是分别问市场规模、技术可行性、差异化，再用你自己的公式合成。好处是优先级变化时你改的是代码里的系数，不用重写提示词。

拆解：输入 → 多级选项 → 返回

输入 客服工单文本（一段自然语言）
第 1 步 账单 技术 退款 账户 其他
第 2 步 紧急 一般 低
返回
Step 1 → { category: "账单", conf: 0.88 } Step 2 → { priority: "紧急", conf: 0.93 }
置信度策略 每步独立判断置信度：> 0.85 进入下一层；< 0.85 在该层扩展更细的选项子集，或直接路由到人工。
应用层要点
  • 一次问满比拆多次更高效：Jev 的并行 sampler 允许一次请求同时回答多个独立问题。处理一张发票时，可以同时判断发票类型、异常风险、审批级别和是否需要人工复核。
  • 问题命名按测量对象，而非操作意图：用 is_time_sensitive 而不是 route_to_incident，前者能跨策略变更复用，后者一旦路由规则变了就得改提示词。
  • 阈值收敛到一个配置对象：不要让你的阈值散落在十几个 if-else 里。把所有置信度阈值集中管理，改一行全生效。

维基百科“通往哲学”路径映射

🧭 浏览器导航

场景与挑战

“通往哲学”是维基百科的一个经典挑战：从任意词条出发，只点第一个链接，最终几乎总能到达“Philosophy”条目。它本质上是一个路径搜索问题。

John 用这个场景来对比两种思路：LLM 试图把整个页面当作“无限画布”来处理，容易迷路；Jev 则把页面上的所有可点击链接当作有限的决策集，每一步只回答“下一个链接点哪个”。

这是一个把 DOM 交互视为决策问题的样板——它不是“让 AI 浏览网页”，而是“让 AI 在候选链接中做选择”。

拆解：输入 → 选项 → 返回

输入 当前页面 URL + 目标页面（Philosophy）
选项 页面上所有可点击链接（动态生成）
返回
nextLink: "Philosophy" conf: 0.79
置信度策略 conf > 0.8 直接点击；0.5–0.8 回退到备用链接（排序第二）；< 0.5 记录路径失败并重启。每一步都可以单独验证。
应用层要点
  • DOM 交互 = 决策集，不是自由画布：把页面上所有可操作元素（按钮、链接、表单）作为一个 Choice 的选项集，Jev 只回答“下一步操作哪个”。
  • 每一步独立可验证：路径导航的最大优势是——出问题只影响一步，不影响整条链。每步的 conf 低于阈值时可以回退或重新选择。
  • 状态管理在代码层：Jev 不维护上下文，每次调用都需要你把当前页面状态（URL、可见元素列表）作为 state 传入。
8

实时演示教练

🎤 实时反馈

场景与挑战

演讲者在台上讲，希望有人实时提醒：“市场分析这点还没讲到”“你现在跑题了”“商业模式已经覆盖”。传统做法是真人教练，成本高且难以规模化。

传统 LLM 的秒级延迟无法支撑这个场景——演讲者不可能等 AI 两三秒后再给反馈，讲座节奏早就走完了。

Jev 实时监听语音转写，与预先设定的要点清单交叉比对，毫秒级返回每个要点的覆盖状态，还可以追踪主题漂移。

拆解：输入 → 选项 → 返回

输入 实时语音转写 + 要点清单
[问题陈述, 市场分析, 解决方案, 商业模式]
选项 每个要点的状态：未覆盖 部分覆盖 已覆盖
返回
checkpoint: "市场分析" status: "已覆盖" conf: 0.91
置信度策略 > 0.85 自动勾选；0.6–0.85 标记为“可能已覆盖”但仍高亮提醒；< 0.6 不做判断，避免误报打断演讲者。
应用层要点
  • 滑动窗口而非全量上下文：实时场景下不要传整场演讲的转写，而是传最近 30–60 秒的滑动窗口 + 已覆盖状态摘要，控制输入 token 量。
  • 用 Noul 做二值判断：“当前窗口是否覆盖了‘市场分析’要点？”这是一个典型的 Noul 问题——返回 0–1 概率，代码用阈值判断是否勾选。
  • 在 shadow mode 验证阈值：TypeSafe 建议先用影子模式记录 Jev 的判断和实际结果，用自己的标注数据校准阈值后再开启自动化。
🧠 额外演示：多智能体协调与避碰。多个智能体同时运行时，Jev 实时分析各智能体状态，通过“即时规划”把它们引导到不同路径，避免碰撞与资源冲突。Jev 负责快速局部决策（“下一步往哪走”），更慢的推理模型（System 2）提供战略建议（“整体目标是什么”）而不中断 Jev 的实时控制。

✅ 生产部署检查清单

上线前必须验证的 6 件事

来自 TypeSafe 官方文档和早期采用者的实践总结。

1. 影子模式验证阈值

在生产流量上以 shadow mode 运行 Jev，记录每次判断的置信度和实际结果。用你自己的标注数据校准阈值，不要直接使用别人的默认值。

2. 锁定模型版本

Jev 仍在快速迭代中。在生产环境锁定模型版本（如 jev-1.13），不要使用 jev-latest。版本升级前重新验证阈值。

3. 设计降级路径

Jev 调用超时或返回低置信度时，代码必须有降级策略：升级到更大的 LLM、路由到人工队列、或返回安全的默认值。永远不要让 Jev 的失败阻塞主流程。

4. 确定性逻辑保留在代码中

Jev 当前版本按字面读取指令，不擅长计数，日期视为文本。数学运算、日期解析、安全规则——这些必须由你的代码处理，不要交给 Jev。

5. 置信度阈值按风险分层

不要所有决策用同一个阈值。高风险操作（资金、删除、对外通信）用 > 0.95，低风险操作（分类、标记、排序）用 > 0.75。

6. 记录完整决策链

每次 Jev 调用记录：输入 state 摘要、每个问题的答案和概率、最终决策、触发的阈值规则、延迟和 token 用量。没有这些日志，你无法调试也无法迭代阈值。

⚠️ 何时仍需要完整生成模型：
  • 开放式推理与创意生成：Jev 只做“选择题”，不写文章、不生成代码、不做长链推理。
  • 图像与音频处理：Jev 只读文本，需先转换或配对其他模型。
  • 代码生成与复杂 Agent 上下文压缩：这些任务需要生成式模型的完整能力，Jev 在此场景可能削弱 prompt caching 带来的节省。
