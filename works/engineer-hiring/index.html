How Do You Hire Engineers When AI Writes the Code?

嘉宾 Raymond Wang · CTO & 联合创始人 · Ease Health · 主持人 Amir
时长 28 min · 2026-08-07 · 原链接
Editor's Brief · 节目主线

这期节目表面在谈「招聘」，实际在回答一个更深的问题：当 AI 能写代码，软件工程的价值链到底在哪里？ Raymond 从 Ease Health 的实践出发，论证了一条完整的逻辑链——

首先，招聘标准必须重排：语法和语言熟悉度的重要性下降，取而代之的是产品直觉、工程判断力、热情与驱动力。核心论据是「AI 生成代码的门槛趋近于零，但判断生成结果对不对的门槛没有下降」。这引出一个面试设计的难题：观察候选人 prompt 的过程引入了主观性，因为不同 prompting 风格可能产生同等优秀的结果。

接着他推导出两个实践落点：Code Review 是 AI 最强的工程用例（因为「验证他人产出」正是人类的核心竞争力），以及Token 经济学——用最强模型处理高风险决策（如 code review），用便宜模型处理低风险内部任务，本质是 ROI 思维。

最后收束到角色分化：未来软件工程可能分裂为精英通才、较窄角色和高度专业化专家三层。贯穿全程的金句是："Evaluate the output more than the subjective input."

Ⅰ 招聘标准：什么变了，什么没变
02:05

招聘权重重排

语法知识不再稀缺，产品直觉与工程判断力成为核心信号
  • 语法 & 特定语言熟悉度 → 重要性显著下降
  • 产品直觉（product instincts）：能否从用户视角思考？
  • 工程判断力（engineering judgment）：面对模糊问题时能否做出合理取舍？
  • 热情与驱动力（passion & drive）：依然是不可替代的筛选信号
  • 核心能力：拆解问题 + 引导跑偏的 Agent 回到正轨
"We weigh a lot more on product instincts, engineering instincts, and the ability to break down problems."
05:30

面试设计困境

观察候选人 prompt 引入了主观性——不同风格可能产出同等好结果
  • 传统面试假设「过程可见 = 能力可评估」
  • 但 prompting 风格高度个人化，风格 ≠ 质量
  • 核心矛盾：评价「输入」天然主观，评价「输出」更客观
  • 解法：让面试贴近真实工作，评估最终产出的质量
"Different prompting styles can produce equally strong results."
08:40

编码面试 vs 模型进化

当模型能力每月跃迁，静态面试题的半衰期趋近于零
  • 传统算法题 → 模型轻松通过 → 区分度消失
  • 「不要用 AI」的面试 = 考察一个已经不存在的工作方式
  • 方向：考察「如何用 AI 解决问题」而非「能否不用 AI」
Ⅱ 工程实践：AI 改变了哪里
12:10

Code Review 是最强用例

AI 擅长生成，人类擅长验证——review 恰好是验证的极致形态
  • Agent 生成代码 → 需要有人审查 → 这个「有人」就是工程师的新核心
  • Ease Health 已在跑 background agents 做 code review
  • 类比：医生不看 AI 的诊断报告就签字 = 不可接受
  • 深层含义：「理解代码」比「写代码」更重要
"Use the strongest models for expensive mistakes, such as code review."
14:40

Token 经济学

把 token 支出与工程产出对比——这是 ROI 思维，不是成本削减
  • 关键问题：每个 token 花出去，换来了多少工程价值？
  • 策略：强模型 → 高风险决策（review、架构）；便宜模型 → 低风险内部任务
  • 隐含前提：模型路由（model routing）是工程能力，不是财务问题
  • Ease Health 自建 harness → 统一观测 token 消耗与产出质量
贯穿

Internal AI Harness

不是用现成工具，而是把 AI 编织进日常工作流的「缰绳」
  • 背景 agents + code review agents + 统一工具链
  • 工程师既是使用者也是改进者 → harness 本身是被工程师持续优化的产品
  • 这是「工具链」在 agentic 时代的新形态
"Build an internal AI harness that engineers use and improve as part of their daily workflow."
Ⅲ 未来图景：角色如何分化
26:45

角色分化

软件工程可能分裂为精英通才、较窄角色、高度专业化专家
  • 精英通才：端到端交付，AI 放大个人产出至团队级别
  • 较窄角色：深耕某一层（如 infra、security），AI 辅助但不替代
  • 高度专业化专家：领域知识 + AI 工具 = 不可替代的组合
  • 共同点：「只会写代码」这一层被压缩
"Software engineering may split between elite generalists, narrower roles, and highly specialized experts."
◆ 贯穿全期的元能力（暗线）

判断力（Engineering Judgment）

整期节目的最高频词——它不写代码，但决定代码对不对
  • 贯穿：招聘 → 面试 → review → token 决策 → 角色分化
  • 本质：在不确定性中做出合理取舍的能力
  • AI 放大它：判断力越强 → AI 产出越好；判断力越弱 → AI 放大错误

问题拆解（Problem Decomposition）

Raymond 反复强调的核心能力——把模糊需求变为 AI 可执行的规格
  • 「Break down problems methodically」出现于 02:22
  • 拆解质量直接决定 AI 输出质量 → 这是新时代的「写代码」
  • 对应架构师角色：不是写实现，而是定义接口与边界

Agent Steering（引导跑偏的 Agent）

Raymond 的原话——当 AI 走错方向时，你能察觉并纠正
  • 原文："the ability to break down problems and guide AI agents when they go in the wrong direction"
  • 这是「判断力」的动态版本：不只是评估，而是实时纠偏
  • 对应 harness 的迭代改进：工程师不断调整 agent 行为

验证闭环（Verify & Take Ownership）

从 code review 延伸到整个工程文化的核心动作
  • AI 生成的每一行 → 必须有人验证 → 验证者承担所有权
  • Karpathy 的 "generation-verification loop" 概念
  • 「理解代码」是验证的前提 → 基础能力反而更重要
+ 外部交叉验证（旁注层）
2025

YC 数据：AI 加速的真实上限

Y Combinator 批次数据显示 10x+ 速度提升，但天花板清晰
  • 2025 批次中大量 startup 用 AI agents 实现 10x 工程速度
  • 但「最后一公里」仍需人类：集成、调试、生产化
  • 验证了 Raymond 的「判断力」论点：速度不是瓶颈，判断是
来源：Y Combinator
2025

Gartner 警告：Agent 失控风险

对 Raymond 乐观叙事的必要制衡
  • 预测：到 2028 年 33% 的企业软件将包含 agentic AI
  • 但 "agent sprawl"（智能体蔓延）是真实风险
  • 反向验证了「Agent Steering」的必要性
来源：Gartner
框架

Value Stack：价值栈

把 Raymond 散落的直觉系统化为三层模型
  • Layer 1：Problem Decomposition & Specification（= 拆解）
  • Layer 2：Rigorous Verification & Validation（= review + 验证）
  • Layer 3：System Architecture & Integration（= harness + 架构）
  • 精确对应节目主线 → 这不是新框架，而是 Raymond 论点的结构化表达
来源：unvritt.com
2026

Addy Osmani：行业级佐证

Google Cloud AI 工程总监的两年预测，与 Raymond 高度共振
  • 核心观点：AI 不会消灭程序员，但会淘汰「只会写代码的 coder」
  • 初级门槛提高：新人须能用 AI 交付整个团队的产出
  • T 型人才更值钱：一技之深 + AI 赋能的广度
  • 直接验证了 26:45 的角色分化预言
来源：Addy Osmani / LinkedIn
工程化

Model Routing：模型路由

Raymond "强模型用于高风险" 的直觉 → 已被工程化为标准实践
  • 原则：强模型做规划 & review，快模型做执行 & 批量任务
  • Planner-Executor 分离：可控性强，强模型规划 + 确定性校验
  • 这正是 Raymond 14:40 的 token 经济学的工程落地
来源：腾讯云 / 2026 面试题汇总
案例

领域知识（Ease Health 自身）

Ease Health 的商业模式本身就是对「领域知识不可替代」的沉默证明
  • Ease Health：行为健康领域的 AI-native 操作系统
  • 统一 CRM + EHR + RCM → 需要深度理解医疗报销逻辑、临床工作流
  • a16z $41M Series A → 投的不是「会写代码」，而是「懂这个行业的团队 + AI」
  • 领域知识是「判断力」在具体行业中的具象化
