The Folder Is the Agent

Kieran Klaassen · Every / Cora · 交互解读（最佳实践版）
这篇文章在讲什么？ 作者花了 3 个月尝试用多个 AI agent 协作干活，结果发现问题不在 AI 不够聪明，而在上下文不够。 核心洞察：一个 agent 是什么水平，取决于你给它哪个文件夹——文件夹里装着它的记忆、规则和工具。 本文教你如何把“一个文件夹”变成“一个专家”，以及为什么不该一上来就搞复杂编排。
⓪ 背景

作者是谁？他遇到了什么问题？

Kieran Klaassen 是 Cora 的创始人——Cora 是一个真实在运营的 AI 日历助手产品（帮你安排日程、管理会议）。他花了 3 个月，用多个 AI agent 协作来加速 Cora 的开发，结果令人失望：agent 越多，人反而越累。

先说清两个词，后面通篇都用：
· Agent——能读文件、跑命令、连工具的 AI 助手（本文指 Claude Code 这类编程 agent）。
· 上下文（context）——agent 工作时能看到的所有信息：代码、文档、规则、历史记录。上下文越干净、越对口，agent 越靠谱；上下文一杂，它就胡说八道。
"AI agents don't have a speed limit, but the person managing them still does."
大白话：10 个 agent 同时交差，你得到 10 份结果，却没有足够上下文判断哪个可信。AI 再快，审核的人成了瓶颈。
专家视角：多 agent 演示常是 theatre——一次性成功 ≠ 可复用系统。能并行 ≠ 该并行。
Ⅰ 核心洞察

Agent = 模型 + 文件夹（文件夹就是它的记忆）

同一个 AI 模型，指向不同的文件夹，就变成完全不同的“专家”。

"Just by changing the folder and not the model, I have a different agent."
背景：这说的是 Claude Code 的工作方式。Claude Code 这类编程 agent 打开一个项目时，会自动读取项目根目录里的 CLAUDE.md 当"系统指令"。所以你写在 CLAUDE.md 里的每句话，都等于在告诉它"该怎么干这个项目"。这也解释了为什么"换个文件夹就换了个 agent"。
类比：想象一个实习生。你给他《公司手册》+ 项目文档，他能干活；给他《运维手册》+ 服务器日志，他也能干活。AI 也一样——文件夹就是它的入职培训。文件夹里装的东西，就是它的全部世界。
文件夹里有什么（2026 年的标准结构）
  • CLAUDE.md / AGENT.md — 给 AI 的“员工手册”：命名规范、架构决策、常见陷阱
  • .claude/skills/ — 给 AI 的“操作手册”：如何连数据库、如何查日志
  • docs/ — 项目文档、事故复盘
  • bin/ — 自动化脚本（调度器、健康检查）
怎么写好 CLAUDE.md（官方给出的写法标准）
  • 用 /init 起步。Claude Code 的 /init 会扫描你的代码库自动生成一份 CLAUDE.md 草稿（构建命令、测试约定、项目规范都帮你推断出来），你再往上补它推断不出来的部分，而不是从零写。
  • 控制在 200 行以内。CLAUDE.md 会在每次会话开头加载、计入 token——越长，遵循度反而越差。写不下就拆到子目录的 CLAUDE.md 或 .claude/rules/，按需加载。
  • 指令要"可验证"，不要写口号。"用 2 空格缩进"能被照做，"代码写规范一点"会被当成废话。官方给出的准绳是：如果 AI 照字面执行这条指令，得到的结果是不是你想要的？
  • 定期清冲突。两条规则互相矛盾时，AI 会自己挑一条执行，结果不可预测。定期扫一遍 CLAUDE.md、子目录的 CLAUDE.md、.claude/rules/，删掉过时和互相打架的条目。
Skills：让"操作手册"按需加载（progressive disclosure）
Skills 是放进 .claude/skills/ 的"能力包"——一份 SKILL.md 加可选的示例、模板、脚本。它的聪明之处在于分级加载：启动时只加载每个 skill 的 name + description（几百字），skill 被命中时才加载它的正文，用到的模板和示例才最后加载。这样你能装 100 个 skill，启动时的上下文开销只有几 KB。
最容易被忽略的一点：skill 能不能被用上，基本取决于 description 写没写清"什么时候用"。写得太笼统（比如"API 测试工具"），AI 就永远不会想起它。
专家视角：这套机制有个正式名字——Context Engineering（上下文工程）。Thoughtworks 的定义是"curating what the model sees so that you get a better result"（精心策划模型看到的内容，以得到更好的结果）。它和 prompt engineering 的区别是：prompt 只管"我这一轮怎么说"，context engineering 管的是整个窗口——系统指令、工具定义、检索结果、对话历史、记忆——而这些往往才是 token 的大头。一句话：CLAUDE.md 是"agent 的宪法"，Skills 是"新员工的 onboarding doc"，而上下文工程是让这两者真正生效的学科。
Ⅱ 最佳实践：用“多个文件夹”替代“多个 agent”

两个文件夹 = 两个不同专家（关键：隔离带来安全与专注）

同一个模型（Opus），配两个不同的文件夹，得到两个完全不同的“员工”。这不是技巧，而是构建可靠 AI 系统最重要的一条原则。

文件夹角色知道什么关键边界
~/cora/功能工程师架构、测试约定、组件创建、产品知识只写新功能
~/cora-agent/运维工程师AppSignal、日志、Postgres replica、Intercom、Slack 通知没有 app 代码，绝不会误改生产
为什么要“拆文件夹”（行业里的先进做法）
  • 上下文隔离 = 关注点分离。写代码的 agent 不该看到生产数据库密码，动生产的 agent 不该被业务需求干扰。各管一段，错误不会跨域传染。
  • 权限天然收敛。文件夹里没有的东西，agent 就摸不到。这是最简单也最牢的权限模型——比事后加审批网关更省心。
  • 出错可定位。一个文件夹对应一个职责，出了问题一眼知道去哪查，不用在 10 个 agent 的日志里大海捞针。
  • 资产可累积。CLAUDE.md / runbooks / postmortems 越写越厚，三个月后这个文件夹就成了别人抄不走的壁垒。
你可以照搬的 4 条最佳实践
  • 一个职责 = 一个文件夹。写代码、查数据、做研究、管运营，各开各的目录，绝不混用。
  • 文件夹之间默认不通。不共享上下文、不共享凭证、不共享状态。需要协作就通过文件/文档传递，而不是让 agent 互相对话。
  • 按最小权限配置。“运维”文件夹只给数据库只读 + 日志查看；“写代码”文件夹不给生产环境任何入口。
  • 给每个文件夹一份 CLAUDE.md。写明“你是谁、你管什么、你不能做什么、常用命令有哪些”——这 4 行就是它的岗位说明。
  • 别用一个“万能文件夹”让 agent 身兼十职——上下文一杂，输出就开始胡说。
  • 别让多个 agent 共享同一份上下文，然后用“加审批”来补救——治标不治本。
一句话记住：不要造“10 个全能员工”，要造“5 个各管一段的专家”。文件夹就是它们的工位。
Ⅲ 最佳实践：别把精力花在“调度”上

真正复杂的不是“调度”，而是“文件夹”

调度层其实很简单：一个 Ruby 守护进程 + 文件消息，没有复杂的网络协议。难的是把每个文件夹的上下文写对。

类比：就像项目经理在工单系统里派活——把任务写成文件，worker 在正确的文件夹里被拉起，每 60 秒检查状态。
把文件夹养好的 5 条心法（思维方式）
  • ① 上下文是产品，不是配置。很多人把 CLAUDE.md 当成一次性 prompt 随手一粘。错。它是你持续维护的“产品说明书”，需要像代码一样版本管理、定期更新。
  • ② 先写“不能做什么”，再写“能做什么”。权限和禁区写在前面，agent 才不容易越界。这比事后加审批更省心。
  • ③ 让 agent 读历史，而不是凭空猜。事故复盘、部署日志、决策记录都丢进文件夹——agent 的“经验”来自这里。
  • ④ 调度越朴素越好。文件消息、定时任务、工单系统，够用就行。别急着上复杂的编排框架，那只是把复杂度从“上下文”搬到“调度”。
  • ⑤ 文件夹的结构要稳定。路径一变，agent 的肌肉记忆就废了。定好结构就别乱改，改了要同步更新 CLAUDE.md。
调度伪代码watch(spawn_requests/) → lead agent → 写 subtask_*.md → daemon 在正确文件夹拉起 worker → 写回 result_*.md → 每 60 秒检查状态
专家视角：文件消息很“土”，但可观测、可重放、可调试——比 agent 之间互相喊话更稳。大多数团队缺的不是更好的调度器，而是更干净、更完整的上下文。
Ⅳ 真实代价：多 agent 的三大暗病

44 个 agent 不是“自动跑起来就完了”

规模上来后，会出现三类问题。每类都用“大白话 + 后果 + 怎么防”讲清楚，照着自查就行。

暗病 1 · Encoding bug（编码乱码：看起来没问题，其实崩了）
em dash（—）和弯引号（""''）这类特殊字符，在强制 US-ASCII 的守护进程里会直接报错，作者查了好几周才定位。这类 bug 的特点是不会立刻暴露，往往等到深夜告警才发现。
  • 统一所有脚本、日志、文件用 UTF-8，从源头消灭 encoding bug。
    • 暗病 2 · Context drift（上下文漂移：agent 在干昨天的活）
    agent 用的是旧上下文，或者重复别人已经做完的任务——它不知道“这件事上午有人干过了”。本质是没有共享的任务状态。而这只是 context 失效的四种模式之一：overload（信息太多）、distraction（无关信息被当成重点）、contamination（错误信息混进正确信息）、drift（长时间运行后逐步退化）。
  • 维护一份“当前任务清单”（如 subtask_*.md 的状态字段），agent 开工前先读最新状态，避免重复劳动。
    • 暗病 3 · Agent stalls（卡死：永远显示 working）
    API 调太快会限流，等输入又会无限挂起。状态永远停在 working，人还得手动去救。
  • 给每个任务设超时和重试上限；超时就标记 failed 并报警，绝不静默卡死（stall）。
    • 一个容易低估的放大效应：上下文腐烂会传染
    单 agent 里 context drift 只是它自己输出变差；多 agent 里，Agent A 被污染的产出会作为“事实”进到 Agent B 的上下文，B 的结论再传给 C——每跳一次，错误就被放大一次。这就是为什么多 agent 系统的协调成本随团队规模平方级上升，而不是线性上升。反过来也说明：隔离上下文（参考 Ⅱ）不只是为了专注，更是为了给错误“上防火墙”。
    现实代价：没有自动清理方案时，Kieran 只能定期手动 prune，并接受一部分 token 被浪费。这就是“全自动”背后的隐形成本。
    token 账也要算：单 agent 的 agentic coding 任务约消耗普通聊天的 1000× token，同一任务内也有约 30× 的波动，而准确率并不随开销同步上升。另有实证做法（Bai 等，2026）通过 PLAN.md / INVARIANTS.md + 每轮读取预算 + 子 agent 用带外便签协调，能把长任务的 token 用量压低 70–90%。
    专家视角：多 agent 的隐性成本——状态、归属、回滚、人工审计——全都会回来找你。三个暗病加起来指向同一件事：规模化的难点从来不是“让 agent 跑起来”，而是“让它跑得对、跑得完、跑得可查”。
    Ⅴ 实操框架：不能靠感觉编排

    You can't vibe orchestrate（先会用，再谈自动化）

    这是全文最值得照做的部分：把"上 agent 协作"拆成四步，每一步都有明确的通过标准。跳过任何一步，agent 就会给你开已经做过的 PR、建重复的 issue。

    "Build it, use it, trust it, and then orchestrate it."
    四步走（每步都有验收标准）
    ① Build
    搭好文件夹和 flow
    ② Use
    自己跑到行为可预测
    ③ Trust
    确认可靠再交给调度
    ④ Orchestrate
    机器替你路由
    第 ① 步 · Build：把上下文资产建起来
    • 写好 CLAUDE.md（角色、边界、常用命令、禁区），并纳入版本管理。
    • 把 runbooks、postmortems、架构决策记录（ADR）放进文件夹，让 agent 有"经验"可读。
    • 定好文件夹结构并固定下来——路径一变，agent 的肌肉记忆就废了。
    通过标准：一个新 agent 只读这份文件夹，就能在你不在场时做出 80% 的正确判断。
    第 ② 步 · Use：自己先当 operator
    • 不接调度、不跑并行，先单 agent 单文件夹手动跑一遍，观察它每一轮在做什么。
    • 记录它反复出错的地方，回头补进 CLAUDE.md 或 skills——这是上下文资产增值的过程。
    • 统计它在哪些任务上稳定、哪些任务会飘（context drift / hallucination）。
    通过标准：同一个任务连续跑 5 次，输出偏差在你可接受范围内，行为可预测。
    第 ③ 步 · Trust：量化可靠性
    • 建立小批量验收集：挑 10–20 个典型任务，对比 agent 输出和你的人工预期。
    • 先看"该做没做"（漏召回）和"不该做却做了"（越权）两类错误，再谈加速。
    • 只在限权（read-only / scoped tools）下验证，出错代价可控。
    • 别用"它这次做对了"当证据——单点成功无法证明稳定，那是 vibe 不是证据。
    通过标准：在限定权限内连续 N 次无越权、无重复劳动，你才敢把它的产物直接合并。
    第 ④ 步 · Orchestrate：才上调度
    • 用最简单的 dispatcher（文件消息 / 工单 / 定时任务）派活，让 lead agent 按 task manifest 分发。
    • 给每个 subtask 设超时、重试上限和状态字段，杜绝"永远 working"的卡死。
    • 保持 context isolation：每个 worker 只在自己的文件夹里工作，靠文件传递交接物。
    • 在关键节点（部署、改数据、外发）保留 human approval gate。
    通过标准：你能说出当前每个 agent 在干什么、产出物在哪、失败了谁负责——这就是"可运营"，而不是"在跑"。
    最常见的失败：从 ① 直接跳到 ④。上下文还没养成就上并行，结果不是加速，而是把混乱放大 N 倍——Kieran 的 swarm 经历正是教训。
    专家视角：编排不是起点，是终点。这套四步其实是把"上下文工程（context engineering）"当成了可验证的工程产物，而不是靠感觉调 prompt。上下文成熟了，自动化才安全。
    Ⅵ 行业在往哪走

    从“让一群 AI 乱跑”到“专人专岗 + 平台管运行”

    大白话：过去大家迷恋“10 个 agent 一起干活很酷”，现在行业转向“每个 agent 只做一件事、平台替你管住它”。专业地说，就是从 agent swarm 走向 specialist agents + managed runtime。这跟 Kieran 用两个文件夹拆专家，是同一件事。

    三个阶段，看懂这波变化
    • ① Agent Swarm（群聊模式）一群 agent 各自发言、自由协作，共享上下文。看起来热闹，实际互相干扰、人审不过来。
    • ② Context Isolation + MCP（分槽干活）每个 agent 分到独立上下文窗口，用 Model Context Protocol (MCP) 统一接入工具，不再各自造轮子。
    • ③ Managed Runtime（平台托管）sandboxing / durable state / observability / human approval gate 由平台接管，人只管“同意还是拒绝”。
    两个具体进展（截至 2026 年）
    • MCP 规范 2026-07-28 大改版：协议核心彻底无状态化——删掉了 initialize 握手和会话 ID，每个请求自描述，可以落在普通轮询负载均衡后的任意实例上。新增 Mcp-Method / Mcp-Name 两个 HTTP 头，网关不用解析请求体就能按工具路由、计量和限流；需要中途追问时改用 Multi Round-Trip Requests（服务器返回 input_required，客户端补答后重试原调用）。Tasks 从实验特性转正为正式扩展，并强制对齐 OAuth 2.1。官方同时明确：协议无状态 ≠ 你的应用无状态，需要跨调用保持状态时，由工具返回一个显式 handle 让模型自己在线程间传递。目前 Tier 1 SDK 月下载量已接近 5 亿次。
    • Claude Managed Agents 进入公开 beta：Anthropic 把它做成托管服务，brain（Claude + harness）、hands（sandbox / 工具执行）、session（持久事件日志）三者彻底解耦——harness 崩溃可以 wake(sessionId) 从事件日志恢复，sandbox 变成“可替换的 cattle”而非“舍不得丢的 pet”，凭证也绝不进 sandbox。计费是 token + 会话运行时 $0.08 / 小时（仅按 running 状态计时，idle 不计；另有网页搜索 $10 / 1000 次），并且目前只走 Claude API 直连，不支持 Bedrock / Vertex。
    两种做法，对比一下

    以前：Agent Swarm

    AI 自主性很高
    可控度很低
    一堆 agent 平权协作、共享 memory、自己写 orchestrator。酷，但不可控，context drift 严重。

    现在：Specialist + Managed Runtime

    AI 自主性适中
    可控度很高
    一个 lead agent + 若干 context-isolated subagents，各占独立 workspace，平台管 sandbox / state / tracing / approval。
    行业证据（说人话 + 术语对照）
    行业在做什么（术语）说人话：对你意味着什么
    MCP 规范升级为无状态核心（2026-07-28），Mcp-Method / Mcp-Name 头路由工具接入标准化（M×N → M+N），而且不用再维护会话亲和性、共享会话存储——普通的负载均衡和网关就能跑
    Claude Managed Agents 公开 beta：brain / hands / session 解耦，会话运行时 $0.08 / 小时你不用自己写调度器、管容器恢复和凭证隔离；按小时付费，idle 不收费
    Subagent 模式：lead agent + context-isolated workers一个主脑管多个专职 AI，各干一段、不互相污染
    多 agent 的 token 开销显著更高（单 agent 约 chat 的 4×，多 agent 约 15×；agentic coding 极端情况下可达 ~1000×）别为“并行”而并行，先算账：省下的人工值不值多烧的 token
    Human approval gate / human-in-the-loop 成为标配你的角色从“写代码”变成“把关的人”：关键操作要你点头
    落地建议：不用追新框架。先把“专人专岗 + context isolation”做好（参考 Ⅱ、Ⅲ、Ⅴ），等 managed runtime 能力成熟了再往上叠——这是最稳的路径，也和 Kieran 的路线一致。
    数据口径：token 倍数来自 Anthropic 公开研究与官方文档（subagent 约 4–7×、lead+subagent 最高约 15×），不同任务差异大，仅作量级参考。
    Ⅶ 30 分钟上手（照着做就行）

    把你的文件夹变成“专家 AI”

    大白话：只要你会建文件夹、会写文档，今天就能开始。专业地说：你要创建一个带 CLAUDE.md 的 workspace，并通过 scoped permissions 把它变成一个 context-isolated specialist agent。

    四步走
    ① 写岗位说明
    新建 CLAUDE.md
    ② 开两个工位
    worktree：人一个、AI 一个
    ③ 限权
    先给 read-only
    ④ 把关
    approval gate：改数据前你同意
    第 ① 步：先跑 /init，再补你自己的约定（CLAUDE.md）
    在终端里对项目跑一次 /init——Claude Code 会自己扫一遍你的代码库，自动生成一份 CLAUDE.md 草稿（构建命令、测试约定、项目规范都帮你推断出来了）。你只需要往上补它推断不出来的部分：
    · 你是谁（role）：比如“你是这个项目的开发助手”
    · 你管什么（scope）：比如“只管前端页面和组件”
    · 你不能做什么（guardrails）：比如“不能改数据库、不能部署”
    · 常用命令（workflow）：比如“跑测试用 npm test，启动用 npm run dev”
    关键：别从零写，也别抄别人的模板。/init 负责它能看出来的部分，你的规则负责只有你才知道的部分——比如团队的代码风格、历史踩过的坑、哪些是禁区。这也是 context engineering 的核心：精心策划模型看到的内容，而不是堆一堆泛泛的 prompt。（关于 CLAUDE.md 的长度、指令怎么写才有效、Skills 怎么按需加载，见 Ⅰ。）
    第 ② 步：开两个工位（worktree / branch）
    • 一份你自己写代码用，一份交给 AI 跑。两边都改同一个项目，但各改各的——这就是最朴素的 context isolation。
    • 这样你能清楚看到：你在哪一步拖慢了进度、哪一步不敢放手给 AI、哪一步 AI 做得比你好。
    第 ③ 步：只给只读权限（scoped / read-only）
    • 一开始只让 AI “看”和“跑测试”，别让它删东西、发消息、改数据。
    • 等它连续做对十几次，再按最小必要原则开放一点点写权限。
    • 别一上来就把生产数据库密码、支付密钥、API token 丢给 AI——权限给小，出错代价才小。
    第 ④ 步：把“改数据 / 上线”留给你自己（human approval gate）
    删数据、发外邮、部署上线、改配置——这些动作一定让你手动确认。你当“守门员”，AI 当“运动员”。这就是 human-in-the-loop。
    想更进一步：让 AI 从“看文件”到“做实事”（三层栈）
    ① Context Layer（上下文层）CLAUDE.md + 项目文档 + 代码 + 故障记录（postmortems）——它靠这个“上岗”，也是你累积最久的资产
    ② Tools Layer（工具层）通过 MCP servers 接上代码仓库、数据库（只读）、日历、浏览器——让它“动手”，每个 tool 都带 scope
    ③ Runtime Layer（执行层）用托管运行时（managed runtime）或本地守护进程跑它，全程 tracing 留痕、关键动作走 approval gate
    专家视角：文件夹即 agent 的红利不在“多”，而在“上下文资产可累积”。今天写的 CLAUDE.md，三个月后就是别人无法复制的壁垒。
